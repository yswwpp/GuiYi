# 架构决策记录（ADR）

记录项目中的重要架构决策及其背景。

## ADR-001: 采用前后端分离架构

**日期**：2026-04-04

### 背景

需要决定项目的整体架构模式。

### 决策

采用 Swift 前端 + Python 后端的分离架构，通过 HTTP API 通信。

### 理由

1. **前端**：SwiftUI 是 macOS 原生技术，提供最佳用户体验
2. **后端**：Python 在 AI/NLP 领域生态成熟，适合语义索引和数据处理
3. **分离**：前后端独立开发，职责清晰，易于维护

### 后果

- 需要维护两个项目
- 需要 API 文档和接口约定
- 部署时需要同时启动前后端

## ADR-002: 索引优先策略

**日期**：2026-04-04

### 背景

三方平台（飞书、WPS 等）的内容如何存储？

### 决策

采用索引优先策略：三方平台内容只建索引，不存储全文。

### 理由

1. **节省空间**：避免重复存储
2. **避免冲突**：原文档保留在原平台，不会出现版本冲突
3. **合规性**：公司文档不离开公司平台
4. **实时性**：通过增量同步保持索引最新

### 后果

- 需要增量同步机制
- 需要处理平台 API 变更
- 搜索结果需要跳转到原平台

## ADR-003: 使用 txtai 作为语义索引引擎

**日期**：2026-04-04

### 背景

需要选择本地语义索引方案。

### 决策

使用 txtai + BAAI/bge-m3 向量模型。

### 理由

1. **本地运行**：无需云端服务，隐私安全
2. **中文优化**：bge-m3 模型对中文支持良好
3. **易用性**：txtai API 简洁，开箱即用
4. **性能**：支持增量索引，适合频繁更新

### 后果

- 首次索引构建需要时间
- 向量模型占用磁盘空间（约 1-2GB）
- 需要管理索引版本

## ADR-004: Monorepo 项目结构

**日期**：2026-04-04

### 背景

前后端项目如何组织？

### 决策

采用 Monorepo 模式，前后端在同一个 Git 仓库下。

### 理由

1. **统一管理**：一个仓库管理所有代码
2. **版本同步**：前后端接口变更时，一次 commit 同步更新
3. **适合个人项目**：单人开发，不需要复杂的多仓库管理

### 后果

- 仓库体积较大
- 需要清晰的目录结构
- .gitignore 需要区分前后端

```markdown
### 背景

说明决策带来的影响（正面和负面）。
```

2. 添加到本文件中
3. 提交 Git
