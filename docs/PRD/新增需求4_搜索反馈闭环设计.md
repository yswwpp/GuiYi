# GuiYi 搜索反馈闭环设计

## Context

用户在实际使用 GuiYi 搜索时，偶尔会遇到结果质量不理想的情况。当前处理方式是停下工作、定位源代码、描述问题、调整搜索或排序逻辑。这种方式成本高、打断强，也难以积累可分析的数据。

本需求希望在搜索结果页增加一个可选的反馈入口。用户可以对“本次搜索”进行评价；当评价为不满意时，可以补充原因和说明。系统保存本次搜索上下文、搜索结果快照和用户反馈，供后续集中分析，提炼搜索质量改进方向。

目标不是让反馈立即改变搜索结果，而是先建立稳定的数据采集闭环。

---

## 目标

1. 在搜索结果页提供低干扰的“评价本次搜索”入口。
2. 用户可以选择是否反馈，不强制、不阻塞搜索流程。
3. 反馈记录需要包含本次搜索上下文、搜索结果快照、用户评价状态和原因。
4. 反馈数据持久化到数据库，便于后续查询、统计和人工分析。
5. 功能与搜索索引、同步元数据解耦，不影响正常搜索性能和结果。

---

## 非目标

第一阶段不做以下能力：

1. 不自动根据反馈调整索引、embedding 或 rerank 模型。
2. 不把反馈内容写入 txtai 索引。
3. 不在反馈页实现复杂的数据分析看板。
4. 不改变 `/api/search` 当前返回结构。
5. 不强制每次搜索都生成服务端 search session。

这些能力可以在反馈数据积累后作为第二阶段设计。

## 现状调研

### 前端

当前首页搜索界面在：

- `guiyi-client/GuiYi/SearchView.swift`

主要状态：

- `searchText`：当前查询文本
- `searchResults`：当前展示结果，统一使用 `APIClient.AISearchResult`
- `keywordExtractionEnabled`：关键词提取开关
- `rerankEnabled`：Rerank 开关
- `keywordsExtracted`：AI 提取出的关键词
- `processingTime`：搜索耗时
- `rerankUsed`：本次是否实际使用 Rerank

普通搜索 `/api/search` 的结果会在前端转换为 `AISearchResult`，因此反馈入口可以统一基于 `searchResults` 实现，不需要区分普通搜索和 AI 搜索。

> ⚠️ **前置改造项（字段缺失）**：本需求要求快照保存 `doc_type` 和 `extension`，但前端当前的模型并未解析这两个字段：
>
> - `APIClient.AISearchResult`（`guiyi-client/GuiYi/APIClient.swift`）只有 `id/title/url/source/account/score/rerankScore/finalScore/text/aiKeywords`，缺 `docType`、`extension`。
> - 普通搜索的 `APIClient.SearchResult` 同样缺 `docType`、`extension`，转换为 `AISearchResult` 时（`SearchView.performSearch`）自然也带不上。
> - 后端 `AISearchResult` / `SearchResult`（`app.py`）本身是返回 `doc_type`、`extension` 的，问题只在前端模型未接。
>
> 因此实现本需求前，需先在 `APIClient.swift` 的 `AISearchResult`、`SearchResult` 两个模型及其 `CodingKeys` 中补齐 `docType`（映射 `doc_type`）、`extension`，并在 `SearchView.performSearch` 普通搜索分支的 `map` 中透传。否则快照中这两列恒为空，FB-008 的快照断言与“按数据源/类型分析”将无法验证。

### 后端

搜索入口在：

- `guiyi-server/guiyi_server/app.py`

当前搜索接口：

- `POST /api/search`
- `POST /api/ai-search`

索引管理在：

- `guiyi-server/guiyi_server/index/txtai_index.py`

数据库现状：

- 当前运行代码使用 MySQL，`SyncMetadata` 和 `LocalDirectoryStore` 都基于 `pymysql`。
- 早期文档中仍有 SQLite 描述，但与当前实现不一致。
- 反馈数据建议继续使用 MySQL，并新增独立存储模块。

## 设计原则

### 1. 反馈面向“搜索会话”，不是单个结果

用户评价的对象应是“本次搜索整体是否好用”，而不是某一个结果条目。一次搜索质量问题通常包含召回、排序、摘要展示、AI 关键词理解、Rerank 等多个因素，整体反馈更适合后续分析。

### 2. 保存结果快照

反馈提交时必须保存当时展示给用户的结果快照。原因：

- 后续索引可能变化，不能依赖重新搜索复现。
- 排序、分数、摘要和 AI 状态都是判断搜索质量的重要依据。
- 结果快照可以用于分析“目标结果是否出现”“出现但排名过低”“高分结果是否无关”。

### 3. 低干扰

反馈入口应可见但不打断主流程。用户可以不评价；只有用户主动点击反馈入口时才打开反馈页面。

### 4. 与索引和同步解耦

反馈数据是质量观测数据，不是知识内容，也不是同步元数据。不要写入：

- `txtai` 索引
- `metadata.json`
- `sync_metadata`
- Obsidian vault

建议新增独立表和独立 store。

## 用户体验设计

### 入口位置

建议在搜索结果区域顶部或底部增加一个小按钮：

- 文案：`评价本次搜索`
- 展示条件：`showResults == true && !searchResults.isEmpty && !isSearching`
- 样式：轻量按钮，不抢占搜索结果视觉焦点

不建议放在每条结果上，因为本需求评价的是本次搜索整体。

### 反馈页面

点击入口后打开 SwiftUI sheet 或 popover。

字段建议：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| 评价 | 单选 | 是 | `满意` / `一般` / `不满意` |
| 问题原因 | 多选或单选 | 不满意时必填 | 固定原因分类 |
| 补充说明 | 文本框 | 否 | 用户自由输入 |
| 期望结果 | 文本框 | 否 | 用户可以描述“我原本想找什么” |

### 原因分类

建议固定原因：

| code | 展示文案 | 适用场景 |
| --- | --- | --- |
| `missing_expected_doc` | 没搜到应该出现的内容 | 目标文档未召回 |
| `bad_ranking` | 结果排序不对 | 目标文档出现但排名低 |
| `irrelevant_results` | 结果太泛或不相关 | 多数结果不相关 |
| `wrong_summary` | 摘要/预览不足以判断 | 命中但展示信息不够 |
| `wrong_ai_keywords` | AI 关键词理解错 | 关键词提取导致偏题 |
| `rerank_worse` | 智能重排后变差 | Rerank 使排序恶化 |
| `source_missing` | 某个数据源缺失 | 怀疑飞书、本地、网页等数据源未覆盖 |
| `other` | 其他 | 无法归类 |

### 提交后反馈

提交成功：

- 关闭反馈页
- 在结果页显示短暂提示：`反馈已保存`

提交失败：

- 保留用户已填内容
- 显示错误：`反馈保存失败，请稍后重试`
- 不影响当前搜索结果

## 数据模型

第一阶段推荐两张表：一张保存反馈主体，一张保存结果快照。

### search_feedback

```sql
CREATE TABLE IF NOT EXISTS search_feedback (
    id VARCHAR(64) PRIMARY KEY,
    query_text TEXT NOT NULL,
    source VARCHAR(50) DEFAULT NULL,
    account VARCHAR(255) DEFAULT NULL,
    doc_type VARCHAR(50) DEFAULT NULL,
    limit_value INT DEFAULT 20,

    search_mode VARCHAR(20) NOT NULL,
    keyword_extraction_enabled TINYINT(1) DEFAULT 0,
    rerank_enabled TINYINT(1) DEFAULT 0,
    ai_enhanced TINYINT(1) DEFAULT 0,
    rerank_used TINYINT(1) DEFAULT 0,
    keywords_extracted TEXT,
    processing_time_ms DOUBLE DEFAULT NULL,

    rating VARCHAR(20) NOT NULL,
    reason_code VARCHAR(50) DEFAULT NULL,
    reason_text TEXT DEFAULT NULL,
    expected_result TEXT DEFAULT NULL,

    result_count INT DEFAULT 0,
    client_created_at DOUBLE DEFAULT NULL,
    created_at DOUBLE NOT NULL,

    INDEX idx_created_at (created_at),
    INDEX idx_rating (rating),
    INDEX idx_reason_code (reason_code),
    INDEX idx_search_mode (search_mode)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

字段说明：

| 字段 | 说明 |
| --- | --- |
| `id` | UUID 或短随机 ID |
| `query_text` | 用户原始搜索词 |
| `source/account/doc_type` | 搜索过滤条件 |
| `limit_value` | 搜索请求 limit |
| `search_mode` | `normal` / `ai`，表示用户本次走普通搜索还是 AI 搜索 |
| `keyword_extraction_enabled` | 前端开关状态 |
| `rerank_enabled` | 前端开关状态 |
| `ai_enhanced` | 后端是否实际完成 AI 关键词增强 |
| `rerank_used` | 后端是否实际完成 Rerank |
| `keywords_extracted` | JSON 字符串，保存 AI 提取关键词 |
| `rating` | `good` / `neutral` / `bad` |
| `reason_code` | 固定原因 code |
| `reason_text` | 用户补充说明 |
| `expected_result` | 用户期望找到的内容 |
| `result_count` | 本次提交的结果数量 |

### search_feedback_results

```sql
CREATE TABLE IF NOT EXISTS search_feedback_results (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    feedback_id VARCHAR(64) NOT NULL,
    rank_index INT NOT NULL,

    doc_id VARCHAR(255) DEFAULT NULL,
    title TEXT DEFAULT NULL,
    url TEXT DEFAULT NULL,
    source VARCHAR(50) DEFAULT NULL,
    account VARCHAR(255) DEFAULT NULL,
    doc_type VARCHAR(50) DEFAULT NULL,
    extension VARCHAR(20) DEFAULT NULL,

    score DOUBLE DEFAULT NULL,
    rerank_score DOUBLE DEFAULT NULL,
    final_score DOUBLE DEFAULT NULL,
    text_preview TEXT DEFAULT NULL,

    created_at DOUBLE NOT NULL,

    INDEX idx_feedback_id (feedback_id),
    INDEX idx_doc_id (doc_id),
    INDEX idx_source (source),
    CONSTRAINT fk_search_feedback_results_feedback
        FOREIGN KEY (feedback_id) REFERENCES search_feedback(id)
        ON DELETE CASCADE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

### 结果快照数量

默认保存前 20 条结果即可。原因：

- 当前前端搜索默认 limit 多为 10 到 20。
- 反馈分析重点通常在第一页结果。
- 避免反馈表膨胀过快。

后端可设置硬限制，例如最多接受 50 条结果。

```json
  "processing_time_ms": 842.5,
  "rating": "bad",
  "reason_code": "bad_ranking",
  "reason_text": "目标文档在第 12 位，前面很多结果不相关",
  "expected_result": "希望公司飞书里的金融服务规划文档排在前面",
  "results": [
    {
      "id": "doc_001",
      "title": "金融服务规划",

      "account": "company",
      "doc_type": "doc",
      "extension": null,
      "score": 0.63,
      "rerank_score": 0.71,
      "final_score": 0.71,
      "text": "搜索结果摘要..."
    }
  ],
  "client_created_at": 1730000000.123
}
```

#### Response

```json
{
  "status": "success",
  "id": "feedback_abc123",
  "message": "搜索反馈已保存"
}
```

#### 校验规则

| 字段 | 规则 |
| --- | --- |
| `query` | 必填，trim 后不能为空 |
| `rating` | 必须是 `good` / `neutral` / `bad` |
| `reason_code` | `rating=bad` 时必填 |
| `results` | 可为空数组，但不能超过后端上限 |
| `reason_text` | 建议限制 2000 字符 |
| `expected_result` | 建议限制 2000 字符 |
| `text` | 后端截断保存，例如最多 1000 字符 |

> ⚠️ **跨字段校验必须在后端做**：`reason_code` 在 `rating=bad` 时必填属于跨字段约束，Pydantic 默认不会自动校验。需在 request model 上用 `model_validator`（Pydantic v2）显式校验「`rating==bad` 时 `reason_code` 非空」，不满足时返回 422。不能只依赖前端拦截，否则 FB-010（直接 curl 后端）无法通过。

## 后端模块设计

建议新增：

- `guiyi-server/guiyi_server/storage/search_feedback_store.py`

职责：

1. 初始化 `search_feedback` 和 `search_feedback_results` 表。
2. 提供 `create_feedback(payload)` 方法。
3. 对结果数量、长文本做后端截断。
4. 统一处理 MySQL 连接和事务。
5. `keywords_extracted` 入库前用 `json.dumps(..., ensure_ascii=False)` 序列化为 JSON 字符串，不要直接存 Python list 的 `str()`（会产生单引号的非法 JSON，后续分析无法解析）。

不建议把逻辑放入：

- `SyncMetadata`：职责是同步状态。
- `IndexManager`：职责是索引和搜索。
- `AIConfigStore`：职责是 AI 配置。

`app.py` 只负责：

1. 定义 Pydantic request/response model。
2. 调用 `SearchFeedbackStore`。
3. 返回 API 响应。

## 搜索状态快照

反馈提交时要使用“本次已完成搜索”的状态，而不是用户当前输入框的最新状态。

原因：

- 搜索有 300ms debounce。
- 用户可能搜索完成后继续修改输入。
- AI 开关可能在搜索后被切换。

建议在 `performSearch` 成功后保存：

- `lastCompletedQuery`
- `lastCompletedResults`
- `lastSearchMode`
- `lastKeywordExtractionEnabled`
- `lastRerankEnabled`
- `lastKeywordsExtracted`
- `lastProcessingTime`
- `lastRerankUsed`

反馈入口基于这些 `lastCompleted*` 字段，而不是直接读实时 `searchText`。

> ⚠️ **`aiEnhanced` 当前未被前端接收**：后端 `AISearchResponse`（`app.py`）会返回 `ai_enhanced`，但 `SearchView.performSearch` 接收 AI 搜索响应时只取了 `keywordsExtracted / processingTime / rerankUsed`，并未保存 `aiEnhanced`。实现时需在 AI 搜索成功分支补存 `response.aiEnhanced` 到 `lastAIEnhanced`；普通搜索分支固定为 `false`。

> ⚠️ **`processing_time_ms` 仅 AI 搜索有真实值**：`/api/search` 不返回耗时，普通搜索分支当前固定写 `processingTime = 0`。因此普通搜索反馈的 `processing_time_ms` 恒为 0 属于预期行为，不是缺陷。耗时分析只对 `search_mode=ai` 的样本有意义。

## 隐私和数据安全

反馈数据是本地优先数据，仍可能包含敏感信息：

- 搜索词可能包含项目名、客户名、个人信息。
- 结果标题和摘要可能包含敏感内容。
- URL 可能包含平台文档路径。

第一阶段策略：

1. 数据只保存到本地 MySQL，不上传云端。
2. 不保存完整文档内容，只保存结果摘要快照。
3. 后端限制 `text_preview` 长度。
4. 后续如果增加导出功能，需要明确提示导出范围。

## 分析方式

反馈数据积累后，可以按以下角度分析：

### 1. 按原因聚合

```sql
SELECT reason_code, COUNT(*)
FROM search_feedback
WHERE rating = 'bad'
GROUP BY reason_code
ORDER BY COUNT(*) DESC;
```

用于判断主要问题是召回、排序、摘要还是 AI 理解。

### 2. 按搜索模式对比

```sql
SELECT search_mode, rating, COUNT(*)
FROM search_feedback
GROUP BY search_mode, rating;
```

用于判断 AI 搜索是否比普通搜索更稳定。

### 3. Rerank 问题分析

```sql
SELECT COUNT(*)
FROM search_feedback
WHERE reason_code = 'rerank_worse';
```

用于判断是否需要调整 Rerank top_n、模型或融合分数。

### 4. 数据源问题分析

```sql
SELECT r.source, COUNT(*)
FROM search_feedback f
JOIN search_feedback_results r ON f.id = r.feedback_id
WHERE f.rating = 'bad'
GROUP BY r.source;
```

用于判断某些数据源结果质量是否明显偏差。

## 后续演进

### 第二阶段：搜索会话 ID

后端搜索接口返回：

- `search_session_id`
- `results`
- `metadata`

反馈时只提交 `search_session_id` 和用户评价。这样可以减少前端提交体积，也能避免前端漏传状态。

但这会改变 `/api/search` 响应结构，需要谨慎处理兼容。

### 第三阶段：分析看板

增加本地分析页：

- 反馈列表
- 按原因统计
- 按搜索模式统计
- 高频差评 query
- 差评详情回放

### 第四阶段：辅助改进建议

用 AI 对反馈样本做聚类，总结可能的改进方向：

- 调整索引文本构造
- 增加标题权重
- 修改关键词提取 prompt
- 调整 Rerank top_n
- 改善结果摘要展示

## 验收标准

1. 搜索结果页能打开反馈页面。
2. 用户可以评价 `满意` / `一般` / `不满意`。
3. `不满意` 时必须选择原因。
4. 提交后 MySQL 中能看到反馈主体和结果快照。
5. 普通搜索和 AI 搜索都能提交反馈。
6. 反馈失败不影响搜索结果展示。
7. 反馈数据不写入 txtai 索引、不影响同步元数据。
8. 结果快照保存排序、分数、来源、标题和摘要。
9. 长文本会被截断，避免数据库异常膨胀。
