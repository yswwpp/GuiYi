# GuiYi 搜索反馈闭环测试用例

## 测试范围

本文档覆盖“搜索反馈闭环”第一阶段功能测试，包括：

1. 前端反馈入口和反馈表单。
2. 后端 `POST /api/search-feedback` 接口。
3. MySQL 表结构和数据持久化。
4. 普通搜索和 AI 搜索下的反馈快照。
5. 异常、边界和回归场景。

不覆盖：

1. 自动根据反馈优化搜索算法。
2. 反馈分析看板。
3. 搜索会话 ID 机制。

> **空结果反馈口径（统一约定）**：第一阶段策略为「**前端无结果不显示反馈入口，后端接口本身允许空数组**」。两者不冲突——前端通过 `!searchResults.isEmpty` 控制入口可见性，避免用户对空结果误提交；后端为未来扩展（如允许显式反馈“什么都没搜到”）保留接收空数组的能力，此时 `result_count=0`。FB-002 验证前端不显示入口，FB-016 验证后端接口接受空数组，二者预期都成立。

## 测试环境

### 后端

```bash
cd guiyi-server
source .venv/bin/activate
python main.py
```

后端地址：

```text
http://127.0.0.1:8765
```

### 前端

使用 Xcode 运行：

```text
guiyi-client/GuiYi.xcodeproj
```

### 数据库

使用当前 `DB_CONFIG_PATH` 指向的 MySQL 配置。

需要确认表存在：

```sql
SHOW TABLES LIKE 'search_feedback';
SHOW TABLES LIKE 'search_feedback_results';
```

## 测试数据准备

建议确保索引中至少包含以下类型数据：

1. 一个网页文档。
2. 一个飞书文档。
3. 一个本地文件文档。
4. 一次能返回多条结果的 query，例如项目常用关键词。

如当前环境没有稳定测试数据，可使用已有索引中的任意关键词进行手工验证。

## 前端测试用例

### FB-001 搜索完成后显示反馈入口

前置条件：

- 后端服务正常。
- 搜索 query 能返回至少一条结果。

步骤：

1. 打开 GuiYi 搜索窗口。
2. 输入一个能命中结果的关键词。
3. 等待搜索完成。

预期结果：

- 结果列表正常展示。
- 页面出现 `评价本次搜索` 入口。
- 搜索进行中时不应误显示可提交状态。

---

### FB-002 无搜索结果时不显示反馈入口

前置条件：

- 后端服务正常。

步骤：

1. 输入一个极不可能命中的 query。
2. 等待搜索完成。

预期结果：

- 若没有结果，反馈入口不显示，或显示为不可用状态。
- 不出现空结果快照误提交。

备注：

- 本用例验证“前端不显示入口”这一侧；后端接口允许空数组由 FB-016 验证，两者不冲突（见“测试范围→空结果反馈口径”）。
- 如果产品后续决定开放“无结果反馈”，则预期应调整为允许反馈，并将 `result_count=0`。

---

### FB-003 打开并关闭反馈页面

步骤：

1. 搜索并得到结果。
2. 点击 `评价本次搜索`。
3. 点击取消或关闭按钮。

预期结果：

- 反馈页面打开。
- 关闭后回到搜索结果页。
- 搜索结果不丢失。
- 不产生数据库记录。

---

### FB-004 满意反馈可直接提交

步骤：

1. 搜索并得到结果。
2. 打开反馈页面。
3. 选择 `满意`。
4. 不填写原因和说明。
5. 点击提交。

预期结果：

- 提交成功。
- 反馈页面关闭。
- 页面出现 `反馈已保存` 或等价提示。
- 数据库中 `rating=good`。
- `reason_code` 可以为空。

---

### FB-005 不满意反馈必须选择原因

步骤：

1. 搜索并得到结果。
2. 打开反馈页面。
3. 选择 `不满意`。
4. 不选择原因。
5. 点击提交。

预期结果：

- 前端阻止提交，提示需要选择原因。
- 不发送 API 请求，或后端返回错误后前端明确提示。
- 数据库中不新增记录。

---

### FB-006 不满意反馈可填写补充说明和期望结果

步骤：

1. 搜索并得到结果。
2. 打开反馈页面。
3. 选择 `不满意`。
4. 原因选择 `结果排序不对`。
5. 补充说明填写：`目标文档在第 12 位`。
6. 期望结果填写：`希望某个飞书文档排在前 3`。
7. 点击提交。

预期结果：

- 提交成功。
- 数据库保存：
  - `rating=bad`
  - `reason_code=bad_ranking`
  - `reason_text` 与输入一致
  - `expected_result` 与输入一致

## 后端接口测试用例

请求：

```bash
curl -X POST http://127.0.0.1:8765/api/search-feedback \
  -H "Content-Type: application/json" \
  -d '{
    "query": "测试查询",
    "source": null,
    "account": null,
    "doc_type": null,
    "limit": 20,
    "search_mode": "normal",
    "keyword_extraction_enabled": false,
    "rerank_enabled": false,
    "ai_enhanced": false,
    "rerank_used": false,
    "keywords_extracted": [],
    "processing_time_ms": 0,
    "rating": "good",
    "reason_code": null,
    "reason_text": null,
    "expected_result": null,
    "results": [],
    "client_created_at": 1730000000.123
  }'
```

预期结果：

- HTTP 200。
- 返回 `status=success`。
- 返回非空 `id`。
- `search_feedback` 新增一条记录。

## 数据库测试用例

### FB-011 主表和结果表写入一致

步骤：

1. 提交一条带 3 个 results 的反馈。
2. 查询主表：

```sql
SELECT id, query_text, rating, result_count
FROM search_feedback
WHERE id = '<feedback_id>';
```

3. 查询结果表：

```sql
SELECT feedback_id, rank_index, doc_id, title, source, score, final_score
FROM search_feedback_results
WHERE feedback_id = '<feedback_id>'
ORDER BY rank_index;
```

预期结果：

- 主表存在 1 条记录。
- `result_count=3`。
- 结果表存在 3 条记录。
- `rank_index` 从 0 开始连续递增。
- 每条结果的 `feedback_id` 与主表 ID 一致。

## 集成测试用例

### FB-012 普通搜索结果提交反馈

前置条件：

- 关闭关键词提取。
- 关闭 Rerank。

步骤：

1. 在前端输入 query。
2. 等待普通搜索返回结果。
3. 打开反馈页面。
4. 选择 `一般`。
5. 提交。

预期结果：

- 提交成功。
- 数据库：
  - `search_mode=normal`
  - `keyword_extraction_enabled=0`
  - `rerank_enabled=0`
  - `ai_enhanced=0`
  - `rerank_used=0`

---

### FB-013 AI 搜索结果提交反馈

前置条件：

- 开启关键词提取或 Rerank 中至少一个。

步骤：

1. 在前端输入 query。
2. 等待 AI 搜索返回结果。
3. 打开反馈页面。
4. 选择 `不满意`。
5. 原因选择 `AI 关键词理解错` 或其他原因。
6. 提交。

预期结果：

- 提交成功。
- 数据库：
  - `search_mode=ai`
  - `keyword_extraction_enabled` 与搜索时开关一致
  - `rerank_enabled` 与搜索时开关一致
  - `keywords_extracted` 保存为 JSON 字符串
  - `processing_time_ms` 保存为后端返回耗时

---

### FB-014 Rerank 状态正确保存

前置条件：

- 开启 Rerank。
- 后端 Rerank 服务可用。

步骤：

1. 执行一次 AI 搜索。
2. 确认结果页显示 AI 或 Rerank 标识。
3. 提交反馈。
4. 查询数据库。

预期结果：

- `rerank_enabled=1`。
- 如果后端实际使用 Rerank，`rerank_used=1`。
- 结果表中 `rerank_score` 对使用 Rerank 的结果非空。
- `final_score` 与前端显示分数一致。

备注：

- 如果 Rerank 开关开启但服务不可用，允许 `rerank_enabled=1` 且 `rerank_used=0`。
- “`final_score` 与前端显示分数一致”以结果行实际渲染的分数为准（`AISearchResultRow`），本条为 P1 手工比对，不要求自动化精确断言。

## 异常和边界测试用例

### FB-015 后端不可用时前端提示失败且保留输入

步骤：

1. 正常完成一次搜索。
2. 停止后端服务。
3. 打开反馈页面并填写内容。
4. 点击提交。

预期结果：

- 前端显示保存失败。
- 反馈页面不应直接丢失用户填写内容。
- 搜索结果仍保留。

---

### FB-016 结果为空数组时接口行为正确

请求：

```json
"results": []
```

预期结果：

- 如果产品允许无结果反馈：HTTP 200，`result_count=0`。
- 如果产品不允许无结果反馈：HTTP 400，错误说明明确。

当前建议：

- 后端允许空结果，前端第一阶段默认无结果不显示入口。

---

### FB-017 超长文本被截断或拒绝

步骤：

1. 构造 `reason_text` 超过 2000 字符。
2. 构造结果 `text` 超过 10000 字符。
3. 提交反馈。

预期结果：

- 后端不能 500。
- 行为二选一：
  - 截断后保存。
  - 返回 400 并提示字段过长。
- 数据库不会保存无限长文本。

推荐预期：

- `reason_text` 超限返回 400。
- `results[].text` 后端截断保存。

---

### FB-018 结果数量超过上限时后端限制

步骤：

1. 构造 100 条 results。
2. 提交反馈。

预期结果：

- 后端不能 500。
- 行为二选一：
  - 只保存前 50 条。
  - 返回 400，提示结果数量超限。

推荐预期：

- 保存前 50 条，主表 `result_count=50`。

---

## 回归测试用例

### FB-019 搜索功能不受反馈功能影响

步骤：

1. 不打开反馈页面，连续执行普通搜索。
2. 不打开反馈页面，连续执行 AI 搜索。
3. 对比新增功能前的基本搜索行为。

预期结果：

- 搜索请求仍能正常返回。
- 搜索耗时无明显异常。
- 搜索结果点击打开行为正常。
- 不点击反馈入口时不写入反馈表。

---

### FB-020 同步和索引数据不受反馈功能影响

步骤：

1. 提交多条搜索反馈。
2. 执行一次数据源同步。
3. 执行一次搜索。
4. 检查索引元数据和同步表。

预期结果：

- `sync_metadata` 不写入反馈数据。
- txtai metadata 不写入反馈数据。
- 搜索结果中不会出现反馈记录。
- 同步流程不受影响。

## 验收检查清单

- [ ] 前端搜索完成后能打开反馈页面。
- [ ] 用户可以提交满意、一般、不满意三种反馈。
- [ ] 不满意反馈必须选择原因。
- [ ] 反馈提交成功后有明确提示。
- [ ] 反馈提交失败不丢失已填内容。
- [ ] 后端能保存反馈主体。
- [ ] 后端能保存结果快照。
- [ ] 普通搜索反馈能正确标记 `search_mode=normal`。
- [ ] AI 搜索反馈能正确标记 `search_mode=ai`。
- [ ] 关键词、Rerank、耗时等搜索状态能正确保存。
- [ ] 长文本和大量结果有边界保护。
- [ ] 不点击反馈时不产生数据库记录。
- [ ] 反馈数据不进入索引和同步元数据。
